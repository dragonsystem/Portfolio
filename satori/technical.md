# SATORI — 技術的な工夫

## 画像と構造を一緒に渡す

```
選択したフレーム
    ├─ 画像（PNG）として書き出す
    └─ レイヤー構造を JSON にする
         └─ 2 つを一緒に Gemini へ送る
              ├─ issues[]   … 見つかった問題
              ├─ commands[] … 直すための操作
              └─ components[] … コンポーネント化の提案
```

画像だけでは「どのレイヤーか」がわからず、構造だけでは「何のための UI か」がわからない。両方を渡すことで、UI の意味をふまえた指摘と、レイヤーを特定した修正の両方ができる。

---

## AI の出力の形を固定する（構造化出力）

当初は「JSON で返して」と指示するだけだったため、Markdown のコードブロックで返ってくることがあり、取り除く処理が必要だった。
Gemini の `response_schema` で出力の形を指定し、決まった値しか返せないようにした。

| 項目 | 許す値 |
|---|---|
| 問題の種類 | `unnamed` / `absolute_layout` / `redundant_group` |
| 重要度 | `high` / `medium` / `low` |
| 修正の操作 | `rename` / `apply_autolayout` / `ungroup` |

AI の返す修正内容がプラグインの実行できる操作に限られるので、想定外の操作が実行されることがない。

### 問題と修正操作を分ける

最初は修正操作を問題の中に入れ子で持っていた。一括修正（Phase 2）では修正操作だけを順に実行すればよいため、Phase 1 の段階で `issues[]` と `commands[]` に分けた。後から変えると影響が大きいが、この時点なら変更は小さく済んだ。

---

## まとめて修正するときの安全策

| 決めたこと | 理由 |
|---|---|
| 一括適用の前に `figma.saveVersionHistoryAsync` でバージョンを保存 | 結果が気に入らなければ戻せるようにする |
| 1 件ずつの修正ではバージョンを保存しない | 保存が増えすぎると履歴を追えなくなる。1 件なら通常の取り消しで戻せる |
| 実行順は「名前の変更 → Auto Layout → グループ解除」で固定 | データを壊さない順にする（グループを先に解除すると、ほかの操作の対象が消える） |
| 処理中はボタンを押せなくする | 二重の実行を防ぐ |
| 適用済みの項目はグレーにして残す | 何を直したかが後からわかる |

Figma の API では一括の自動ロールバックができないため、終了後に保存したバージョン名と、戻し方の案内を表示している。

## Auto Layout を適用するときの工夫

AI が推測した余白の値をそのまま使うと、見た目が少しずれることがあった。
横並びの場合は、**今の子要素の座標から余白と間隔を計算**して適用する。また適用前に、子要素を見た目の並び順に並べ替えてから Auto Layout にする。

## Figma の制約への対処

| 問題 | 原因 | 対処 |
|---|---|---|
| `??` で構文エラー | Figma の実行環境が新しい構文に未対応 | TypeScript の出力を ES2019 に下げる |
| オブジェクトのスプレッド構文でエラー | 同上 | プロパティを 1 つずつ書く |
| ノードの取得に失敗 | ページを必要なときだけ読む方式（dynamic-page）では同期の取得が使えない | `getNodeByIdAsync` に変更 |
| コンポーネント内の Auto Layout が直らない | インスタンスはプラグインから変更できない仕様 | 対象の種類を確認してから適用する |

## API キーの扱い

API キーは `figma.clientStorage`（使っている端末の中）に保存する。Gemini との通信は画面側（ui.html）で行い、キャンバスを操作する側は外部と通信しない。
