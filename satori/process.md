# SATORI — 開発プロセス

## タイムライン

```
2026-06-03  Phase 1（MVP：解析と 1 件ずつの修正）、Phase 2（まとめて修正）
2026-06-12  Markdown 書き出し、指摘の言語設定、Auto Layout 適用の改善
2026-06-13  ウィンドウのサイズ変更
```

開発中、自分（プロデューサー）が出した指示と決定を時系列で記録した。何を作ったかだけでなく、なぜそう決めたかを残すため。

---

## Phase 1 — 解析して 1 件ずつ直す

### 優先順位の決め方

| 指示 | 内容 |
|---|---|
| 「エラー・空状態の UX 整備だ」 | AI の精度を上げるより先に、エラー時や結果がないときの表示を整える |
| 「まず git を立ち上げてから、プロンプトの調整に進む」 | いつでも戻せる状態を先に作る |
| 「プロンプトの精度調整は後回しにしよう」 | まだ使った時間が短く、精度について具体的に判断できる段階ではない |

### エラー表示

| 状態 | 表示 |
|---|---|
| 解析前 | 「解析できること」の説明 |
| 認証エラー | 赤い帯と「設定を開く」ボタン |
| 利用上限 | 黄色い帯と、エラー文から読み取った再試行までの秒数 |
| 通信エラー | 青い帯 |
| 問題なし | 成功のカード |
| 信頼度が低い（0.7 未満） | 理由と注意書き |

### 信頼度の説明

「信頼度が 100% になる条件は何か？」と確認したところ、AI 自身による評価なので 100% にはならないとわかった。説明がないと意味が伝わらないため、設定画面に説明を追加した。

### 動かないボタンの修正

「ノードへ移動」「修正を適用」が動かない問題は 2 回報告し、3 つの原因を特定して直した（イベントの受け取り方、ノード取得の非同期化、スプレッド構文）。

## Phase 2 — まとめて修正

### 決めたこと

| 指示 | 結果 |
|---|---|
| 「単体と一括の両方で保存すると、バージョンが多すぎて把握しにくい」 | バージョン保存は一括のときだけ |
| 「チェックボックスは修正操作があるものだけ」 | 直せない指摘には選択肢を出さない |
| 「一括適用をキャンセルしやすい UI にしたい」 | 自動のロールバックは API 上できないため、保存したバージョン名と戻し方の案内を表示 |
| 「安全な順序を優先する。データを壊さないことが最も重要だ」 | 実行順を固定 |
| 「処理中はボタン操作を無効にしよう」 | 二重実行の防止 |
| 「適用済みはグレーにして残そう」 | 直した内容を後から確認できる |

## UI の調整

| 指示 | 結果 |
|---|---|
| 「SATORI という文字はパネル内に要らないのでは？」 | Figma のパネルにすでに名前が出ているので削除 |
| 「フレーム未選択のときは、ボタンを押せない表示にしてラベルを『フレームを選択してください』に」 | ボタンに状態の表示も任せ、ヘッダーの同じ文言は削除 |
| 「説明エリアはボタンの下に」 | 最初に目に入るのは解析ボタンにする |
