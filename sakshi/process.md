## コンセプトの修正

最初は SATORI と同じく「ファイル全体を調べる構造チェッカー」として設計しかけたが、次の指示で方向を変えた。

> 全ファイルを自動でスキャンする必要はない。ライブラリのコンポーネントが想定どおりに使われているか、スタイルやバリアントがデザインシステムの意図どおりに使われているかを確認したい。

これにより SAKSHI は「構造の品質」ではなく「**デザインシステムに沿っているか**」を見るツールになった。

---

## 意思決定ログ

| 問い | 選択 | 理由 |
|---|---|---|
| ライブラリが使われていないことの判定 | ファイル内のコンポーネントもライブラリのインスタンスもない場合に警告 | 両方ないときだけが「未設定」 |
| AI 解析を入れるか | 入れるが任意にする | ルールのチェックだけでも価値がある |
| スキャンの範囲 | まずは 1 フレーム。複数フレームは後で | 先に精度を上げる |
| 直接指定の色 | 最初はすべて報告し、使ってみてから照合を足す予定だった | — |
| ↑の変更 | テストの前に照合を先に実装 | 検出が 1,000 件を超え、ノイズの見極めすらできなかった |
| ローカルのコンポーネント | 問題かどうかは利用者が決める。全ルールを ON / OFF 可能に | 「純粋な観察者」という考え方に合う |
| 結果の並び順 | AI の検出を上、ルールの検出を下 | 任意で有効にした機能の結果を目立たせる |

## 組織内リリースに向けた改善（2026-06-12〜13）

- 結果をルール別にまとめて表示し、検索と重要度の絞り込みを追加。ノード別の表示にも切り替えられる
- ウィンドウの大きさをドラッグで変えられるようにし、大きさを記憶
- チームライブラリのスタイルとも照合し、対応するスタイル名を表示
- Variables が 1 つもない場合の「気づき」を、色だけでなく全種類の Variables で判定
- 公開できるよう、試験的な API の設定を外した
