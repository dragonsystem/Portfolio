# SAKSHI — 技術的な工夫

## 誤検知を減らす：デザインシステムとの照合

最初は、色を直接指定している箇所をすべて問題として扱っていた。実際のファイルで試すと**検出が 1,000 件を超え**、本当に直すべきものが埋もれた。

そこで、スキャンの前にデザインシステムの情報（スタイル・Variables）を一度だけ集め、**対応するスタイルや Variables が存在する場合だけ**問題として報告するように変えた。

```
スキャン開始
  └─ デザインシステムの情報を 1 回だけ集める
       ├─ ローカルのスタイル・Variables
       └─ チームライブラリのスタイル（REST API）
  └─ フレーム内を全階層たどる
       └─ 直接指定の色を見つけたら照合
            ├─ 対応するスタイルがある → 「直せる問題」として報告（スタイル名も表示）
            └─ ない → 未承認の色（任意のルール。標準は OFF）
```

- 報告するのは「直し方がわかる問題」だけにする
- 照合の対象がないときは、「検出されなかった」のか「調べる対象がなかった」のかがわかるよう注記を出す
- Variables が 1 つも定義されていないファイルでは、問題ではなく「気づき」として知らせる

---

## ルールを利用者が決める

ローカルのコンポーネントを使うことが問題かどうかは、チームによって違う。そこで、壊れたインスタンス以外のすべてのチェックを、設定で ON / OFF できるようにした。

「純粋な観察者」という名前のとおり、良し悪しの基準はプラグインではなく利用者が決める。

---

## AI 解析は任意にする

AI 解析は、API キー・モデル名を設定し、「AI を解析に利用する」をオンにしたときだけ動く。ルールにもとづくチェックだけでも十分に役立つため。

### 存在しないレイヤーを指すのを防ぐ

最初は画像だけを AI に渡していたため、AI が存在しないレイヤー ID を返し、「ノードへ移動」が動かなかった。
SATORI と同じく、レイヤー構造（JSON）も一緒に渡すことで、実在するレイヤーを指せるようにした。

---

## 大きなファイルでも止まらないようにする

フレーム内を深さの制限なく調べるため（スタイルや Variables は深い階層にも使われる）、大きなフレームでは時間がかかる。
スキャン中は定期的に処理を区切って画面を更新し、待っている間の案内も表示している。

## Figma の制約への対処

| 問題 | 原因 | 対処 |
|---|---|---|
| インスタンスの元コンポーネントを取れない | dynamic-page では同期の取得が使えない | `getMainComponentAsync()` |
| スタイル一覧を取れない | 同上 | `getLocalPaintStylesAsync()` など |
| `catch {}` でエラー | Figma の実行環境が新しい構文に未対応 | `catch (_e) {}` |
| スプレッド構文でエラー | 同上 | プロパティを 1 つずつ書く |
| 公開できない | 試験的な API を有効にしていた | 設定を外して公開可能に |
| リサイズのつまみが反応しない | 結果一覧のスクロールバーに隠れていた / ポインターイベントの扱い | 配置を直し、マウスイベントで検出 |
