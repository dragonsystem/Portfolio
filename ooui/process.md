# OOUI プラグイン群 — 開発プロセス

## タイムライン

```
2026-05-08〜09  Modeler の要件定義書（v1 → v3 → v3.7）
2026-05-10      Modeler を組織内に公開
2026-05-15〜18  View View を開発（Modeler との連携、ワイヤーフレーム生成）
2026-06-02〜03  Modeler の開発記録・マニュアルを整備
2026-06-04      Modeler Pro の要件定義書と、3 本の共通仕様書（Modeler Spec）を作成
2026-06-05      Modeler Pro を開発
```

開発の体制は、プロデューサー（要件定義・業務の知識・判断・テスト）と、AI（コードの作成・設計の提案・不具合の原因調べ）の分担。どのプラグインでも「なぜそう決めたか」を後から追える開発記録を残した。

## Modeler — 出発点

### 解決したかった問題

業務 SaaS の設計の初期に OOUI のオブジェクトモデルを手で作ると、次の問題があった。

1. **見えないオブジェクトの見落とし**：「承認する」というアクションがあれば「承認の履歴」というオブジェクトも必要になる。業務を知らないと気づきにくい
2. **図を描く手間**：箱を作って文字を入れ、矢印を引く作業を、設計を変えるたびにやり直す
3. **図と資料のずれ**：キャンバスの図と仕様書を別々に管理し、同期が取れなくなる

そこで「業務の説明から AI がモデルを推論し、Figma に直接描く」ことにした。

### 決めたこと

| 問い | 選択 | 理由 |
|---|---|---|
| どの AI を使うか | Gemini API | JSON での出力が安定し、プラグインから直接呼べる（サーバーが要らない）。配布するとき、サーバーの運用や認証の管理が発生しない |
| UI の枠組み | 使わない（素の TypeScript） | この規模では導入の手間に見合わない |
| 仕様ブロックの色 | 黒い背景 | オブジェクト（白）ではなく補足情報であることを、見てすぐわかるようにする |
| プラグインからのオブジェクト削除 | 作らない | キャンバスで選んで Delete を押す方が早い |
| 業務の説明の履歴 | 作らない | 仕様ブロックにすでに残っており、そこからコピーできる |
| 例を見せるプロンプト | 使わない | トークンが大きく増える。プロジェクト固有の例は前提の欄で渡す |

## View View — モデルからワイヤーフレームへ

Modeler でモデルを作ったあと、それをもとにワイヤーフレームを手で作る工程が残っていた。これを自動にするために作った。

### 進め方

1. **土台の修正**：ビルドされない、プロパティが画面に反映されない、詳細画面が未実装、などの問題を直して動く状態にした
2. **Modeler との連携**：Modeler のカードが読めない問題を、共有用の保存（`sharedPluginData`）を足して解決
3. **ワイヤーフレームの質を上げる**：最初の出力は「ワイヤーフレームと呼ぶには遠く及ばない」という評価だった。型に合わせた入力部品、ツールバー、ページ送りなどを加えた
4. **担当者ごとの画面と関係の表示**
5. **カード型の一覧、表示型の詳細画面、アプリの枠**
6. **Auto Layout への統一とコードの整理**

### 決めたこと

| 問い | 選択 | 理由 |
|---|---|---|
| ワイヤーフレームの作り方の順番 | コードで描く → AI → コンポーネント | 必要な部品の粒度を見極めてからコンポーネントにする |
| 詳細画面の「編集する」ボタン | 表示型にだけ固定で置き、Modeler 側の編集系アクションは除く | 同じボタンが 2 つ出るのを防ぐ |
| 区切り線 | 四角形ではなく枠線で表す | Auto Layout の中で扱いやすく、要素が増えない |
| サービス名やメニュー項目 | 端末に保存して次回も使う | 毎回入力し直す手間をなくす |

## Modeler Pro — 上級者のための入口

### なぜ作ったか

Modeler は、AI がオブジェクトを抽出することを前提にしている。しかし OOUI に慣れたデザイナーは、AI との対話を自分で進めてモデルを作り、その結果を Figma に写したい。
そこで、Mermaid を入口にした Modeler Pro を作った。

| 観点 | Modeler | Modeler Pro |
|---|---|---|
| 対象 | 初級〜中級者 | 上級者 |
| 入力 | 業務の説明 | Mermaid |
| AI の役割 | オブジェクトの抽出（必須） | アクションと担当者の補完（任意） |
| 価値 | 考えを広げて、まとめる手助け | まとまった設計をすぐ図にする |

### 先に仕様を書く

着手する前に、要件定義書と、3 本で共通の仕様書（Modeler Spec）を作った。これが実装の根拠になり、Modeler Pro の出力を Modeler とまったく同じ形式にできた。描いたカードは、そのまま View View で使える。

### 決めたこと

| 問い | 選択 | 理由 |
|---|---|---|
| 画面の切り替え | タブをやめ、Modeler と同じく見出しが切り替わる方式に | 複数のプラグインを使い分けるときに迷わない |
| 描画ボタンが画面外に押し出される | 画面下に固定 | 中身の量に関係なく、常にボタンが見える |
| AI の時間切れ | 時間切れをやめ、キャンセルボタンに | 時間切れの本来の目的（止まったままになるのを防ぐ）はキャンセルで代わりにできる。処理時間を利用者が決められる |
| 担当者の色 | 固定の対応表をやめ、登場順に割り当て | 日本語の担当者名がすべて同じ色になっていた |
| プロンプトのテンプレート | 対話を始めるとき用と、変換するとき用の 2 種類 | 上級者には原則の説明は要らない。変換だけを短く指示できる方が使いやすい |

## 今後の予定（未実装）

- **ドメイン駆動設計との連携**：アクションをイベントストーミングの付箋に、オブジェクトを集約に対応させる。オブジェクトをまとまり（境界づけられたコンテキスト）ごとに FigJam のセクションに分ける。どちらも AI が判断しにくい部分があり、精度が課題
- **テンプレートの編集**：今はコードに書いてある業務テンプレートを、設定画面で追加・編集できるようにする
