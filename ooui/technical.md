# OOUI プラグイン群 — 技術的な工夫

## 3 本をつなぐ仕組み

### キャンバス上のカードを「共通の形式」にする

3 本のプラグインは、Figma 上のオブジェクトカードを介してデータを受け渡す。カードは次の形で描く。

```
Frame: "[日本語名]"            ← ID などを pluginData に保存
  ├── Frame: "[technicalName]"  ← 見出し（日本語名 + 英語名）
  ├── Frame: "Properties"
  │     └── Text: "・ 名前 (techName) : type [Actor]"
  └── Frame: "Actions"
        └── Text: "▶ 名前 (techName) [Actor]"
```

- プロパティは `・`、アクションは `▶` で始める。キャンバスのテキストを読み戻すとき、正規表現で区別できるようにするため
- 見出しには日本語名と英語名の両方を出す。日本語で業務を考えるチームが使い、書き出し先（TypeScript や Mermaid）では英語名が必要になるため
- この形式は「Modeler Spec」という仕様書にまとめ、3 本すべてがそれに従う

### プラグイン間でデータを共有する

当初、View View からは Modeler が描いたカードを見分けられなかった。
Figma の `setPluginData` は、**書き込んだプラグインからしか読めない**ためである。

| 方法 | 評価 |
|---|---|
| Modeler 側で共有用の保存に切り替える | 正しいが、Modeler の内部処理に影響が出る |
| View View 側で別の方法で見分ける | 判定があいまいになる |
| **両方に書く** | 採用 |

```typescript
// Modeler 内部用（Modeler だけが読む）
frame.setPluginData("modeler_id", id);

// プラグイン間の共有用（名前空間 "ooui"）
frame.setSharedPluginData("ooui", "modeler_id", id);
frame.setSharedPluginData("ooui", "relations", JSON.stringify(relations));
```

`pluginData` は内部用、`sharedPluginData` は共有用という Figma API の考え方に沿っている。名前空間を `ooui` にそろえたので、あとから 3 本目の Modeler Pro もそのまま加われた。

## Modeler：AI にモデルを推論させる

### プロンプトで OOUI の原則を明示する

```
【原則】
- オブジェクト ＝ ユーザーが操作する名詞（画面・タスク・フローは除外）
- プロパティ ＝ 属性と状態。型は string / number / boolean / Date / string[] から選ぶ
- アクション ＝ オブジェクトに直接作用する動詞（画面の移動は除外）

手順：① 名詞を洗い出す → ② プロパティとアクションを定義 → ③ 関係を整理 → ④ JSON で出力
```

- 「画面」や「手続き」をオブジェクトにしてしまう誤りを、原則として先に禁止する
- 手順を順に考えさせて、抽出の精度を上げる
- 型をすべて `string` にしないよう、選べる型を指定する
- 関係の指定には Figma のノード ID ではなく英語名を使うよう指示する（AI がノード ID を作り出してしまうのを防ぐ）

最初のプロンプトでは「担当者（アクター）」と「オブジェクト」を取り違える誤りが出たため、推論を強めた第 2 版に作り直した。

### プロジェクトの前提を渡す

設定画面に「アクター」「ドメインの用語」「命名ルール」の 3 つの欄を設け、入力があるものだけをプロンプトに加える。

例をいくつも見せる方式（few-shot）は、使うトークンが大きく増えるため採らなかった。プロジェクト固有の例は、この前提の欄で渡す。

### 既存のモデルを更新する

フレームを選んで実行すると、カードのテキストを読み戻して AI に渡し、提案との差分を表示する。

| モード | 動作 |
|---|---|
| 上書き | プロパティとアクションを AI の出力で置き換える |
| 追加 | 既存を残し、新しいものだけを足す（英語名が同じなら既存を優先） |

## Modeler Pro：上級者の成果物を取り込む

### 表記ゆれに強い読み込み

AI が出力した Mermaid には表記のゆれが入る。2 段階で扱う。

| 段階 | 対象 | 動作 |
|---|---|---|
| 自動で直す | 型名の大文字・小文字、引用符の有無、余分な空白 | 何も言わずに正規化する |
| 一覧で見せる | 存在しないオブジェクトへの関係、対応していない記法 | 問題を一覧にし、続行か中止かを選ばせる。問題の箇所だけ除いて続けることもできる |

### AI は「決めない」

AI による補完は任意で、結果はオブジェクトごとに「適用 / スキップ」を選ぶ。上級者の判断を AI の提案より優先する、という考え方による。

AI の処理は時間が読めないため、時間切れで止める方式をやめ、利用者がいつでも止められる「キャンセル」ボタンにした。

### 担当者の色を動的に割り当てる

最初は担当者を英語の 3 種類に決め打ちで色分けしていたため、AI が日本語の担当者名（申請者・承認者など）を返すと、すべて同じ色になった。
固定の対応表をやめ、**登場した順に 6 色のパレットから割り当てる**方式に変えた。この色は、View View で担当者ごとの画面を作るときの手がかりにもなる。

## View View：カードからワイヤーフレームを作る

### 型から入力部品を選ぶ

プロパティの型に合わせて部品を描き分ける。

| 型 | 部品 |
|---|---|
| `string` | 文字の入力欄 |
| `number` | 数値の入力欄（右寄せ） |
| `Date` | 日付の入力欄（カレンダーのアイコン） |
| `boolean` | 切り替えスイッチ |
| 選択肢 | セレクトボックス |

### 実装の順番

| 方法 | 内容 |
|---|---|
| 1. コードで描く | 型の情報から部品をコードで描く |
| 2. コンポーネントを使う | 事前に用意した Figma のコンポーネントを配置する |
| 3. AI でレイアウト | Gemini でレイアウトの構成を作る |

**1 → 3 → 2 の順**で進めると決めた。先にコンポーネントを用意すると、どの粒度の部品が必要かがわからないまま作ることになる。まずコードで描き、繰り返し出てくる部品を見極めてからコンポーネントにする。

### Auto Layout の落とし穴

生成する画面はすべて Auto Layout で組む。その中で、Figma API の順序の制約に当たった。

- 親が「中身に合わせる（Hug）」で、子が「親に合わせる（Fill）」だと、互いに相手の大きさを待つ循環になる。親子の設定の組み合わせを決めて避けた
- 子を「親に合わせる」にする設定は、子を親に追加した**後**でないと効かない

### Figma の実行環境の制約

| 問題 | 対処 |
|---|---|
| プラグイン本体のコードがビルドされない（UI を 1 ファイルにまとめる設定との相性） | UI は Vite、本体は esbuild で別々にビルド |
| `catch {}` の構文でエラー | 出力を ES2017 に下げ、`catch (_e) {}` に書き換え |
| フォントの太さ「Semi Bold」が使えない | Inter の Medium と Bold の 2 種類に統一（Modeler とそろえる） |
